# Phase 0 Research: Session Panel Quota Display

**Verification baseline:** OpenChamber [v2.7.3](https://github.com/openchamber/openchamber/releases/tag/v2.7.3), commit `cf18602cc77146f35e26e103dbee1ab8e218b663`, the latest stable release checked on 2026-11-20. Recheck at delivery; the baseline does not narrow [REQ 2](../../docs/REQUIREMENTS.md#req-2).

## Panel integration — blocked for a stock-host extension

- **Decision:** Keep an installable OpenChamber guest tab as the preferred UI candidate, subject to confirming that a new right-rail tab satisfies REQ 3. Do **not** approve an extension-only design on the current SDK: the read and visibility paths needed by the spec have not been established.
- **Rationale:** The [manifest supports `contributes.panel.entry`](https://github.com/openchamber/openchamber/blob/cf18602cc77146f35e26e103dbee1ab8e218b663/packages/sdk/API.md#L521-L565). [Web and Electron support guest panels](https://github.com/openchamber/openchamber/blob/cf18602cc77146f35e26e103dbee1ab8e218b663/packages/docs/content/docs/extensions.mdx#L8-L30); mobile opts in and VS Code does not load them. [Instance-scoped `host.storage`](https://github.com/openchamber/openchamber/blob/cf18602cc77146f35e26e103dbee1ab8e218b663/packages/sdk/API.md#L258-L264) fits REQ 4. But the [guest frame is sandboxed](https://github.com/openchamber/openchamber/blob/cf18602cc77146f35e26e103dbee1ab8e218b663/packages/ui/src/components/layout/PluginPane.tsx#L539-L618), its [network access is restricted](https://github.com/openchamber/openchamber/blob/cf18602cc77146f35e26e103dbee1ab8e218b663/packages/sdk/API.md#L704-L717), and the [service callback API](https://github.com/openchamber/openchamber/blob/cf18602cc77146f35e26e103dbee1ab8e218b663/packages/sdk/src/service-host.ts#L107-L129) offers no host quota read. The quota role contributes data **to** the host. [Inactive guest tabs may stay mounted](https://github.com/openchamber/openchamber/blob/cf18602cc77146f35e26e103dbee1ab8e218b663/packages/ui/src/components/layout/ContextSurfacePanes.tsx#L654-L677), while documented [SDK lifecycle events](https://github.com/openchamber/openchamber/blob/cf18602cc77146f35e26e103dbee1ab8e218b663/packages/sdk/API.md#L68-L80) do not report tab visibility. The [guest service environment](https://github.com/openchamber/openchamber/blob/cf18602cc77146f35e26e103dbee1ab8e218b663/packages/web/server/lib/guests/service.ts#L525-L541) also does not inherit the usual CA and proxy variables.
- **Alternatives considered:** Ask approval to plan an upstream host change that exposes an authenticated, normalized quota read and panel visibility to the guest, then prove both on the pinned host. If REQ 3 means embedding in an existing first-party panel, plan a native host feature instead. A separate Work Status widget, OpenCode Desktop plugin, or shell command does not prove equivalent placement. Reimplementing all readers inside a guest service still leaves visibility, credential scope, trust, and parity unresolved. Do not route around the SDK sandbox.
- **Acceptance evidence after a path is chosen:** Render one synthetic provider in the agreed surface; show that switch, collapse, close, and application hide stop automatic refresh; restart two isolated instances and verify preferences do not leak; prove success and failure payloads never expose upstream secrets. Source inspection is not this runtime proof.

## Built-in quota inventory

- **Decision:** Start with the pinned host quota registry and cross-check it against the model provider catalog, tracking authentication and plan variants separately. Do not equate a route ID to a unique model provider or infer ineligibility from missing registry entries.
- **Rationale:** The [web registry](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/web/server/lib/quota/providers/index.ts#L49-L249) has 28 dispatchable IDs and the [Usage UI](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/ui/src/lib/quota/providers/index.ts#L8-L36) lists 27: `github-copilot-addon` is dispatchable but not in the UI list; an internal `openai` reader is not registered. `GET /api/quota/providers` identifies configured readers, not eligible model providers or successful fetches. The [model catalog](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/ui/src/stores/config/providers.ts#L179-L212) is separate and location-scoped. [Active-credential selection](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/web/server/lib/opencode/auth.ts#L72-L124) and [provider-specific credential sources](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/web/server/lib/quota/DOCUMENTATION.md#L35-L100) mean a configured provider may still have an unsupported plan or credential type.
- **Alternatives considered:** Use all model catalog entries (model access does not imply quotas); use configured results as the acceptance inventory (limited to the current instance, accounts and credentials); declare the 28 readers full coverage (unmatched model providers remain unverified).

Pinned dispatch IDs: `claude`, `cline-pass`, `codex`, `cursor`, `deepinfra`, `deepseek`, `exe-dev`, `google`, `antigravity`, `hyper`, `zai-coding-plan`, `zhipuai-coding-plan`, `kimi-for-coding`, `openrouter`, `nano-gpt`, `github-copilot`, `github-copilot-addon`, `minimax-coding-plan`, `minimax-cn-coding-plan`, `ollama-cloud`, `wafer`, `opencode-go`, `opencode` (Zen), `neuralwatt`, `kilo`, `zenmux`, `xai`, `mistral`.

## Data quality and refresh constraints

- **Decision:** Normalize both provider and per-model windows, distinguish `ok` from HTTP success, and use valid absolute reset times. Only use an independently verified **full** duration or start/end pair to compute the benchmark. Track balances, counters, and lifetime limits separately from recurring windows; their scope still needs review.
- **Rationale:** The [host payload](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/ui/src/lib/quota/fetchQuota.ts#L5-L38) can include provider and model windows, optional percentage, duration, and reset. `windowSeconds` is not reliably a duration: [Cursor uses time remaining](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/web/server/lib/quota/providers/cursor.ts#L240-L337), [Go can omit it](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/web/server/lib/quota/providers/opencode-go.ts#L99-L156), and [OpenRouter](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/web/server/lib/quota/providers/openrouter.ts#L33-L66) can pair a fixed 30 days with a calendar reset. A missing value is not zero. OpenCode V2's experimental usage limits are [Console budgets and Go allowance](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/web/server/lib/quota/DOCUMENTATION.md#L142-L153), not a general quota API; the host attaches Console budgets under `usage.consoleBudgets` separately.
- **Alternatives considered:** Compute pace from every reported duration (gives incorrect values); invent a reset for non-recurring limits (misleading); substitute OpenCode Console budgets for provider data (incomplete and different semantics).

The [stock UI schedules checks every three minutes while visible](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/ui/src/stores/useQuotaStore.ts#L413-L449) with a 15-second reopen suppression. This is **not** a provider rate limit. The dispatcher [coalesces in-flight checks](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/web/server/lib/quota/providers/index.ts#L278-L287), and [Claude may return cached success in a cooldown](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/web/server/lib/quota/providers/claude/index.ts#L14-L99). A recent response timestamp does not establish fresh upstream data. The stock UI [retains prior results on failed refresh](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/ui/src/stores/useQuotaStore.ts#L229-L267), unlike FR-003. Establish provider limits and freshness evidence before setting production cadence; do not copy the host's stale-on-failure behavior.

## Adjacent quota plugins

- **Decision:** Use adjacent plugins as evidence for formats and edge cases, not as the Session Panel integration or as proof of coverage.
- **Rationale:** [`slkiser/opencode-quota` v6.3.0](https://github.com/slkiser/opencode-quota/releases/tag/v6.3.0) documents OpenCode TUI and OpenCode Desktop UI, not an OpenChamber Session Panel mount. Its [snapshot and refresh RPC](https://github.com/slkiser/opencode-quota/blob/v6.3.0/src/rpc.ts#L195-L216) is a candidate server-side adapter, not a mounting mechanism. [Rows](https://github.com/slkiser/opencode-quota/blob/v6.3.0/src/core/types.ts#L39-L67) have optional remaining percentage, reset, and window start; [provider snapshots](https://github.com/slkiser/opencode-quota/blob/v6.3.0/src/core/types.ts#L98-L110) can include both an error and last-good rows. Its [custom formats](https://github.com/slkiser/opencode-quota/blob/v6.3.0/docs/readme/providers.md#custom-providers) also support local estimates and user field mappings, which this feature does not admit. A read-only adapter would need to prove host access, scope isolation, compliant scheduling and masking of failed-provider stale rows.
- **Alternatives considered:** Install this existing plugin as-is (does not demonstrate REQ 3); copy its provider catalogue (different eligibility criteria); adapt its DTO or an individual supported format after checking window identity, remaining quota, and reset time. Its documented manual refresh behavior is not permission to exceed provider limits.

## Verification approach

- **Decision:** Use deterministic synthetic fixtures and a controlled clock for automated checks; validate native mounting and instance isolation separately in the pinned host.
- **Rationale:** The feature has several independent failure states and threshold boundaries. Provider accounts cannot reliably reproduce them on demand. Fixture tests need no live credentials; any live provider smoke test should be separately authorized and use the host's normal certificate trust without disabling verification.
- **Alternatives considered:** Live-only tests (not repeatable for expiry, rate limits, and partial failures); a standalone UI screenshot (does not prove panel placement, visibility events, or persistence).

## Custom providers and credentials

- **Decision:** Treat host-defined and plugin-defined entries as alternative ways to configure one adapter boundary, not two fetch stacks. Host-defined reuse must prove an explicit supported quota format and a server-side credential bound to the intended destination. If that and one plugin-defined format cannot share the boundary simply, bring the source choice back for approval.
- **Rationale:** OpenChamber's [existing custom-provider setup](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/web/server/lib/opencode/DOCUMENTATION.md#L374-L379) configures model APIs, not quota APIs. The [host deliberately refuses browser access to the credential list](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/web/server/lib/opencode/DOCUMENTATION.md#L267-L297), and the host web process cannot read variables from an external OpenCode process. [OpenCode V2 server integrations](https://opencode.ai/docs/build/plugins/server/#integrations) and [typed plugin RPC](https://opencode.ai/docs/build/plugins/rpc/) are candidate capabilities, not proof that the Session Panel can call them. The v2.7.3 host declares [OpenCode 2.2.4 as its minimum](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/web/server/lib/opencode/compatibility.ts#L30); prove the path first on the bundled 2.3.2 and test any older compatibility before claiming it.
- **Alternatives considered:** Deriving a quota URL from a model URL (no supported discovery contract); reading raw credential lists or databases (wrong trust boundary); arbitrary field mapping (out of scope). One plugin-defined format means no format picker. Require explicit owner setup, dedicated credential references, and approved HTTPS destinations; no credential reuse against a different origin or raw secrets visible to the panel. Verify custom CA trust in the process making the request; [OpenCode's network guide](https://opencode.ai/docs/network/#certificates) describes CA configuration but does not prove it for a new plugin transport.
- **Evidence still needed:** Demonstrate one safe host binding and one plugin-only entry with synthetic credentials, including credential switching, disabling, and two-instance isolation. No live requests or credential reads were performed in this research.

The native [quota-provider extension role](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/web/server/lib/quota/DOCUMENTATION.md#L102-L117) is a distinct candidate: host approval is scoped to named provider IDs; it passes those raw entries to the guest **service**, not to the browser. For a dedicated server-side quota credential, prefer not to request model credentials. Do not treat this role as a general credential broker or give the guest UI the service's credential payload.

## Refresh and accessibility defaults

- **Decision:** Coalesce concurrent refresh triggers per provider/account at the boundary that actually calls upstream. Use the source's minimum interval and honor its reported retry time for automatic, manual, and reset refreshes. A visible countdown or benchmark update is local, not another provider request. Use a visible status label or equivalent non-color cue alongside warning and danger colors.
- **Rationale:** [HTTP `Retry-After`](https://httpwg.org/specs/rfc9110.html#field.retry-after) defines both seconds and an absolute time. Even when a request is delayed, an expired bar must not look current. [WCAG 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) explains why a meaningful color needs another visual cue.
- **Alternatives considered:** Treat manual refresh as unlimited (contradicts provider limits); infer a universal polling rate without provider evidence; rely on color alone (warning and danger would be inaccessible).

## Product decisions to carry forward

- **The benchmark-only fallback needs review.** [Living REQ 1](../../docs/REQUIREMENTS.md#req-1) requires the benchmark for each displayed window, while [FR-002](spec.md#functional-requirements) omits it when timing is insufficient. Keep the living requirement authoritative until the fallback is approved there; do not invent a window start or mark a missing estimate as zero.
- **Coverage is evaluated against a release, not a frozen provider list.** Record the tag, credential/plan variant, source of quota data, known missing fields, and evidence grade. A temporary failure cannot make a supported provider ineligible. Plan evidence is not proof that every provider was tested with an account.
- **Phase 1 requires a selected host path.** A substitute surface, host fork, or extra permission is a scope decision, not an engineering default. Keep implementation and runtime smoke tests separate from Phase 0 unless explicitly authorized.
